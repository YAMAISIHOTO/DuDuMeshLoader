# TacZ Mesh Loader：SBM 2.5.1 网格管线复刻记录

## 背景

`0.1.7-smooth.1` 只启用了导出法线，并关闭旧 VBO 后逐帧走 CPU 顶点提交。实机结果是圆滑效果未得到确认，高面数武器则出现严重卡顿。日志证明该版本被正常加载、模型也成功读取，因此问题不在安装，而在实现并没有完整复刻“永无止境：载具”所用的网格管线。

`0.1.7-sbm.1` 完成了网格管线复刻；`0.1.7-sbm.2` 在不修改 TaCZ 本体的前提下，
补齐 ocular、division、scope_body 与 ocular_ring 的 poly_mesh 特殊渲染；
`0.1.7-sbm.3` 继续修复枪身 poly_mesh 与倍镜 stencil/AR 生命周期错位；
`0.1.7-sbm.4` 修复 attachment 特殊子树误入 QUADS 路径造成的圆滑回归；
`0.1.7-sbm.5` 补齐 TaCZ 遗漏的目镜可见状态并恢复特殊节点的原生 CULL 语义；本轮
`0.1.7-sbm.6` 恢复 scope 目镜原贴图颜色，并修复闲置第一人称的镜片深度穿透。版本仍使用
原 mod id `taczmeshloader`，是原版、`smooth.1`、`sbm.1` 与 `sbm.2` 的直接替换版本。

## 已复刻的读取语义

1. `polys` 支持 `tri_list`、`quad_list` 和索引多边形三种表示。
2. 索引角点按 `[positionIndex, normalIndex, uvIndex]` 读取；省略后两项时沿用 SBM 的 `positionIndex` 默认值。
3. 重复写在多边形末尾的闭合首点会按坐标去除，退化三角形会跳过。
4. 四边形固定拆为 `(0,1,2)` 与 `(2,3,0)`，更多边形使用扇形三角化。
5. 优先保留模型导出的逐角点法线；法线缺失或长度接近零时，才用该三角形的叉积法线回退。
6. 不在运行时按位置平均邻面，也不增加平滑角阈值。圆滑面与硬边都由模型导出的 `normalIndex` 决定。

SBM 原生使用 `(-X,+Y,+Z)`，而本模组历史上已经按 TaCZ 骨骼验证为 `(+X,-Y,+Z)`。为了不把现有枪模镜像，本实现只复刻算法语义，继续保留 TaCZ 坐标适配；法线同步使用 `(+NX,-NY,+NZ)`。

### 客户端圆滑开关

客户端配置文件 `config/taczmeshloader-client.toml` 提供 `smoothNormals`，默认值为 `true`：

- `true` 保持上述既有语义，优先使用有效的导出逐角点法线；
- `false` 忽略导出法线，把每个三角形的三个角点统一替换为该面的叉积法线。

`PolyMeshModel` 在构造时只读取一次配置快照，并把同一值传给模型内的全部 `PolyMesh`，
避免运行中出现部分骨骼已切换、部分骨骼仍使用旧法线的混合状态。法线随后仍沿用现有的
TRIANGLES、骨骼 normal matrix、Oculus 与 AR 管线；开关不修改拓扑、UV、材质、CULL、
stencil 或倍镜层级。

本版本有意不实现热键、热重载和逐帧即时切换。修改配置后必须完整重启游戏；
旧模型的 `close()` 会同时释放 VBO 与 AR 局部网格缓存，因而新模型不会继续使用旧法线缓存。

## 三角渲染与性能

- 主体 poly_mesh 改用 `DefaultVertexFormat.NEW_ENTITY + VertexFormat.Mode.TRIANGLES`，不再把三角形复制第四点后塞进 QUADS。
- cutout RenderType 的状态与 SBM 2.5.1 一致；透明骨骼保留本模组原有的 translucent-cull 业务状态，只改为 TRIANGLES。
- 枪、配件、弹药、方块、LR Tactical 以及延迟透明刷新均使用同一 memoized 三角 RenderType。
- `additional_magazine` 的 FunctionalRenderer 由 TaCZ 提供 QUADS consumer，继续保留 `a/b/c/c` 兼容输出。
- 倍镜 `renderTempPart` 中的 poly_mesh 不再写入 cube 的 QUADS consumer，而是在同一 stencil 阶段使用独立的 TRIANGLES/cutoutCull consumer 并立即刷新；因此 attachment 既保留 SBM 的逐角点法线插值，也与 TaCZ 原生 entityCutout 的正反面剔除一致。
- AR 可用时，首次把局部三角网格构建成 `IMesh` 缓存；后续每帧只提交骨骼位置矩阵、法线矩阵、光照、颜色与 overlay。
- AR 不可用或当前场景不允许加速时，回退到逐顶点 VertexConsumer，并对法线应用当前骨骼 normal matrix。
- 旧 VBO 代码保留但默认关闭，因为它无法向实体着色器同步骨骼 normal matrix。

## 倍镜 ocular/division 兼容

TaCZ 的倍镜遮罩不是普通透明材质，而是由 `BedrockAttachmentModel.renderTempPart()` 在多个
stencil 阶段反复绘制特殊骨骼。原 TacZ Mesh Loader 虽然收集了 ocular mesh 名称，却只在
`super.render()` 结束后按 `stencil == 0` 补画整个模型；纯 mesh ocular 没有在此前写入模板，
因此 division 无法得到正确的可见区域。

`sbm.2` 使用客户端 Mixin 包装 `renderTempPart()` 中唯一的 `BedrockPart.render()` 调用：

1. 先完整保留 TaCZ 的 cube 渲染，混合 cube/poly_mesh 枪包无需改动。
2. 在同一个祖先 PoseStack、光照、overlay 与 stencil 状态上同步追加同名 poly_mesh 子树。
3. `sbm.4` 起为特殊 poly_mesh 使用独立的 TRIANGLES consumer；`sbm.5` 将该特殊层
   对齐为原生 CULL。它在 `renderTempPart()` 返回前通过 Oculus 兼容刷新或指定 RenderType
   刷新；不进入 AR/VBO 延迟管线。
4. 特殊直写为保证 ocular/division 模板形状完整，会把全部后代放入单一 cutoutCull
   三角层，并沿用 `_illuminated` 的满亮度传播；普通 attachment pass 仍按透明命名分层。
5. 附件 poly_mesh 的普通 pass 恢复遵守 `BedrockPart.visible`；TaCZ 临时显示并再次隐藏的
   ocular、division、scope_body 与 ocular_ring 不会在 stencil 结束后重复出现。

该桥接自然覆盖 `ocular`、`ocular_sight`、`ocular_scope`、`division` 及其编号节点，因为
节点选择、scope/sight/both 分支、模板值配对与圆形反转仍完全由 TaCZ 原逻辑负责。

`sbm.2` 最初曾把这些三角网格用 `a/b/c/c` 写进 TaCZ 的原生 QUADS/entityCutout consumer。
与此同时，特殊叶骨在 `renderTempPart()` 返回后会被 TaCZ 设为不可见，因而不再进入附件的
普通 TRIANGLES/cutoutNoCull 路径。大多数倍镜的完整主体都位于 `scope_body` 子树，这会让
多个 attachment 同时失去已经验证过的 SBM 圆滑渲染方式，并额外增加约三分之一顶点。
`sbm.4` 保留原生 stencil 时机并恢复三角图元和逐角点法线插值；`sbm.5` 进一步确认
平滑法线不依赖 NO_CULL，因此只给特殊 attachment 层恢复 TaCZ 原生的 CULL，普通
poly_mesh 仍保留 SBM 的 cutoutNoCull 兼容行为。HAMR 的 6405 个三角在 Y 翻转后，
现有 a/b/c 顺序已与导出法线同向，不需要也不能交换 b/c。

目标环境中的 Oculus 1.8.0 会在扩展实体顶点格式的 QUADS 分支调用
`NormalHelper.computeFaceNormal`，再把同一个面法线覆盖到该 quad 的四个顶点；TRIANGLES
分支则保留输入的逐顶点 normal。因而 `a/b/c/c` 不只是额外一个退化三角，在 Oculus 下还会
确定性地把 attachment 的圆滑法线压成面法线。独立 TRIANGLES consumer 是这次回归的直接修复。

### sbm.5 目镜状态补全

对 TaCZ 1.1.8-hotfix 的 `BedrockAttachmentModel` 生产字节码和源码逐分支核对后确认：

1. 非第一人称分支只调用 `renderTempPart(scope_body)` 与 `renderTempPart(ocular_ring)`，
   完全不提交任何 ocular；这是第三人称、展示和 GUI 中镜片消失的直接原因。
2. 纯 sight 只用 ocular 写不可见 stencil 后绘制 division；组合镜同样跳过 sight ocular
   的可见阶段。因此闲置第一人称的实体 sight 镜片也不会出现。
3. scope 的 `renderOcularAndDivision` 会先用 ocular 轮廓从 scope_body 模板中挖孔，随后
   再把同一 ocular 作为可见层绘制。TaCZ 的这次绘制仍使用白色顶点色；“黑色遮罩”只是
   源码注释描述，原版并没有强制 RGB=0。完整凸面 poly_mesh 会显示自身青绿色材质，而
   被 stencil 排除的 scope_body 在该区域既没有颜色，也没有深度，斜视时便会发生穿透。

`sbm.5` 的 Mixin 补齐 TaCZ 缺失的状态：非第一人称在最终普通模型前同步补画全部 ocular；
第一人称 sight/both 仅在瞄准进度接近 0 时、原生流程开始前补画非 scope ocular。cube 与
poly_mesh 分别进入局部 QUADS/TRIANGLES `COLOR_WRITE` RenderType，仍参与深度测试但不写
深度，使后续 division 能稳定覆盖，也避免 Oculus 全批次刷新污染其他实体。开始 aim-in
后不再补画，避免实体镜片与准星争深度。隐藏模板、第三人称物理镜片和闲置 sight 镜片
颜色均不改变。

### sbm.6 第一人称 scope 深度层级

`sbm.5` 曾把 `renderOcularAndDivision` 的可见 ocular 强制染成黑色。这不是 TaCZ 原版逻辑，
实机只能把青绿色穿透变成黑色穿透。`sbm.6` 撤销该染色，cube 与 poly_mesh 都恢复枪包
纹理颜色；同时只在以下条件全部成立时修正镜体这一遍的 stencil 函数：

1. 当前是第一人称且瞄准进度不大于 `1e-4`；
2. attachment 是 scope，并由 `TaczPolyMeshAttachmentModel` 渲染；
3. `scope_body` 和当前生效的 scope ocular 子树都确实包含 poly_mesh。

满足条件时，`renderScope`/`renderBoth` 中原有的 `scope_body` `renderTempPart` 临时使用
`GL_ALWAYS`，调用返回后在 `finally` 中恢复 `GL_EQUAL, 0, 255`。stencilOp 仍为 KEEP，
ocular 模板与后续 division 配对均不改变；镜体只绘制一次，但会按真实几何写入颜色和
深度，从而挡住位于其后的实体镜片。开始瞄准、纯 sight、第三人称及不含对应 poly_mesh
的传统模型均保持 TaCZ 原路径。

AR 1.0.14 只用于编译其 1.20.1 API，成品 JAR 不内嵌 AR 且没有 mandatory 依赖；玩家
不安装 AR 也能运行。普通 poly_mesh 与枪体仍可使用自有 AR 缓存，但倍镜特殊子树必须
在当前 stencil/color/depth 状态内同步提交，故有意绕开 AR。对高面数 scope 来说，AR
作者所说的“attachment 大部分没有加速”成立，但不是全局永久关闭 AR。

## 枪身 stencil/AR 生命周期修复

`sbm.2` 的枪身入口在 `BedrockGunModel.render()` 完整返回后又渲染了一次 scope attachment，
再补画主体 poly_mesh。这个做法有两个问题：倍镜附件整套流程每帧执行两次；主体 mesh
进入 AR 延迟队列后，代码却立即关闭并清空 stencil，真正绘制时枪身便会穿进镜孔。

`sbm.3` 新增 `BedrockGunModelMixin`，分别接入 TaCZ 1.1.8-hotfix 的两条原生路径：

1. 普通 `render()` 在唯一的 `BedrockAnimatedModel.render()` 调用之后、stencil 清理之前，
   同步提交并刷新主体 poly_mesh。
2. `renderAccelerated()` 在相同调用之后、`-940` 图层和 before/after 回调重置之前，
   只登记 cutout/translucent mesh，不执行 `endBatch` 或任何手动 stencil 操作。
3. 子类只保留一次 `super.render()`，不再重复渲染附件，也不再禁用 TaCZ AR。
4. AR consumer 若意外退化为非加速 consumer，无 scope 时同步回退；有 scope 时则只记录
   一次警告并停止该次主体 mesh，避免在模板尚未生成或已清理后把枪身泄漏进镜孔。
5. 主体 mesh 使用复制当前顶层矩阵的独立 PoseStack；第三方 consumer 或 AR 首次建缓存
   即使抛出异常，也不会把未配平的骨骼栈留给 TaCZ 后续渲染。

生产字节码中的目标调用 owner 是 TaCZ 的直接父类 `BedrockAnimatedModel`，两处均设置
`require = 1`；TaCZ 升级后若调用点变化，应显式失败并重新核对，而不是静默失效。

第一人称原版与 Iris/Oculus 手部路径都以 `LayerDrawType.ALL` 绘制，cutout 与 translucent
共享一次 -940 before/after，因此本轮瞄准修复覆盖这两类主体。世界第三人称渲染可能把
OPAQUE 与 TRANSLUCENT 分相提交；带 scope 且枪身确有透明命名 poly_mesh 的组合仍应
单独实机验证，不能把第一人称结论直接外推到展示实体或第三人称掉落枪。

## 模型数据限制

SBM 自身不会替坏模型重算法线。如果导出文件的共享位置被拆成多个顶点，或者每个角点
本来就写着面法线，完整复刻后仍会保持分面外观。实测发现，测试用 Meshy 修改版曾只对
positions 应用 mesh rotation 与 X 镜像，却没有对 normals 应用相同线性变换；这正是
“已经圆滑但法线方向炸裂”的根因。修复导出器并重新导出 `.geo.json` 后，画面恢复正常。

加载器继续忠实读取导出法线，不针对错误旧模型增加猜测式重算法线。

## `sbm.6-perfdiag.1` 性能诊断包（2026-08-18）

### 目的与边界

- 基线提交：`1977036 fix: restore idle scope lens depth`。
- 该包只增加聚合计时和计数，不改变材质、stencil、深度、AR 缓存或批次提交顺序。
- 诊断只在 JAR 版本号包含 `perfdiag`，或开发环境显式传入
  `-Dtaczmeshloader.perfdiag=true` 时启用；普通 `sbm.6` 构建保持关闭。
- 日志器为 `MeshyLoaderPerf`，每 5 秒输出一次 `[MeshyPerfDiag]` 汇总，避免逐帧日志反过来污染测试。
- 所有 `ROOT` 耗时均为 inclusive：枪根包含附件，附件根包含 normal/special/idle 子阶段，
  各行数值不能直接相加。

### 指标含义

- `gun` / `attachment`：对应 TML 枪模、附件模型入口的总 CPU 墙钟时间。
- `gunPolyAtTaczArStage` / `gunPolyAtTaczNormalStage`：TaCZ 原生枪身 AR/普通阶段内
  追加 poly_mesh 的耗时；前者只表示调用位置，实际 consumer 是否加速应看
  `arStageAccepted` / `fallback`。
- `attachmentNormal` / `attachmentSpecial` / `idleSight`：附件普通 poly_mesh、
  stencil 特殊子树、闲置目镜补画阶段。
- `AR build`：局部 IMesh 首次构建或光影切换后重建；`hits` 为已有缓存命中；
  `write` 仅表示 CPU 向 AR 队列提交，不代表 GPU 已完成绘制。
- `taczCompat`：所有经过 TaCZ `OculusCompat.endBatch` 底层 Function 的调用；
  `fullyBufferedCalls` 是返回 true、调用了 FullyBuffered 无参 `endBatch()` 的子集。
  即使当时缓冲为空也会计一次，耗时也可能包含此前由其他模组或世界渲染排队的几何。
- `withinGunRoot` / `withinAttachmentRoot`：调用发生时所在的最内层模型根作用域；附件会
  覆盖外层枪标签，因此 `withinAttachmentRoot` 包含该附件 `renderTempPart` 内 TaCZ 原生触发的刷新。
  它表示触发位置，不表示全量刷新刷出的全部几何都归属于该模型；未位于这两个根中的调用只进总数。
- `typed`：本项目对指定 RenderType 的 `endBatch(type)`；Oculus FullyBuffered 下通常接近空操作。
- 每个 Timer 同时输出五秒窗口总量、`calls/f` 和 `ms/f`；不同 FPS 的测试应优先比较每帧值。
- 所有计时均为 CPU 渲染线程墙钟时间，可能包含驱动或 GPU 等待；本包没有 GPU timer，
  GPU 瓶颈仍需结合 F3 GPU 占用和分辨率 A/B 判断。AR build/write 在异常时记录的是尝试耗时。

### 实机采样矩阵

关闭光影、保持同一位置与视角，每次切换后等待至少 10 秒，再截取完整的 5 秒诊断窗口：

1. 真空手或史莱姆球。
2. 同一把裸枪，拆除全部附件。
3. 裸枪只安装 HAMR。
4. 当前其他附件全装，并分别记录带/不带 HAMR。

另做一次“全装 + Sundial-Lite”在原分辨率和约一半分辨率下的对照，以区分 GPU 填充率与
CPU/驱动提交上限。测试日志必须从启动开始保留，便于确认实际加载的诊断版本。

## `sbm.6-perfdiag.2` 特殊倍镜细分诊断包（2026-08-18）

### 第一轮实机结论

HAMR 的 `attachmentSpecial` 稳定为 `6 calls/f`、约 `0.925–0.938 ms/f`，占其附件根
约 93%。同一窗口中 AR 始终 `build=0`、`fallback=0`、`write≈0.002 ms/f`，Oculus
`fullyBufferedCalls=0`；因此关光影后的主要热点已经锁定为倍镜特殊子树的同步直写，
不是枪身 AR 缓存失效或 Oculus 全量刷新。

### 新增细分指标

`perfdiag.2` 仍只增加计时和计数，不改变 `getBuffer → 三角写入 → endBatch(type)` 的顺序，
不移动 stencil、深度、PoseStack 或异常处理。每五秒在原四行汇总后追加：

- `SPECIAL_DETAIL precheck/hits`：旧 `attachmentSpecial` 起点之前的
  `hasMeshInSubtree` 资格扫描及命中次数；
- `getBuffer`：只包住特殊 TRIANGLES RenderType 的 `BufferSource.getBuffer`；
- `bonePassInclusive`：从 `findBone` 到特殊子树递归返回，包含骨骼遍历和 mesh 写入；
- `vertexTransformWrite`：逐 mesh 的位置/法线矩阵变换、归一化及 `VertexConsumer` 写入；
- `meshes/vertices`：上述写入调用数与尝试提交的顶点数；
- `boneTraversalExclusive = bonePassInclusive - vertexTransformWrite`：
  `findBone`、可见性判断、PoseStack、骨骼变换、集合查询和递归等剩余开销；
- `typedEndBatch`：特殊路径自己的 `endBatch(type)`，也是原 `typed` 的子集；
- `outerRemainder = attachmentSpecial - getBuffer - bonePassInclusive - typedEndBatch`：
  BufferSource/RenderType 获取、探针边界及其他外层固定开销；
- `SPECIAL_ROOT bone=...`：按 `scope_body`、ocular、division 等本次
  `renderTempPart` 根骨骼分别输出同一组指标。

`vertexTransformWrite` 无法安全拆成“纯矩阵算术”和“纯 consumer 写入”：两者在
`emitTransformed` 中逐顶点交织。强行每顶点计时或改成两遍处理会显著污染结果，甚至改变
异常时已经提交的顶点集合。本轮先保持合并项；`bonePassInclusive`、`vertexTransformWrite`
和 `typedEndBatch` 都是父指标的嵌套子项，不能直接与 `attachmentSpecial` 相加。
两个派生 residual 也会包含极小的 Timer/Map 记账开销，不应用来比较低于约
`0.01 ms/f` 的细微差异；日志中的 `meshes` 表示写入调用次数，不是唯一 mesh 数。

## `sbm.6-perfdiag.3` 顶点快写验证包（2026-08-18）

因此本轮只优化逐顶点位置变换与 `VertexConsumer` 写入，不修改骨骼遍历、stencil 阶段、
RenderType、typed flush 或 AR 状态。

### 快写实现与兼容边界

- 基线提交：`00d79e1 chore: refine attachment performance diagnostics`；
- 旧入口 `VertexConsumer.vertex(Matrix4f, x, y, z)` 在 Minecraft 1.20.1 中会为每个顶点
  创建临时 `Vector4f`，随后再逐项调用颜色、UV、overlay、light、normal 与 `endVertex`；
- 目标实例的 Embeddium 0.3.31 会把上述矩阵位置入口替换为无分配的 `MatrixHelper` 实现，
  因此该实例不能把收益主要归因于减少 `Vector4f`；实际主要待验证的是完整顶点入口能否让
  关闭光影时的 `BufferBuilder` 命中 `NEW_ENTITY fastFormat`；
- 新入口在每次 mesh 写入中只创建一个局部 `Vector4f`，通过同一个 JOML
  `Matrix4f.transform` 入口反复复用，然后调用 14 参数完整 `vertex(...)`；
- `BufferBuilder` 可由该完整入口命中 `NEW_ENTITY fastFormat` 固定布局写入；未重写完整入口的
  第三方 `VertexConsumer` 会自动执行接口默认的逐字段语义；
- Oculus 开启光影时仍由 `endVertex` 注入补充 entity id、midUV 与 tangent；TRIANGLES
  仍读取三个顶点各自的圆滑法线，不使用 raw `putBulkData`，避免扩展顶点步长错位；
- 现有 normal matrix 乘法、逐顶点归一化、颜色、UV、light、overlay、TRIANGLES 与
  a/b/c/c 兼容分支均保持不变；局部复用向量不跨调用共享，保持重入安全。

该改动属于顶点出口的机械优化，不新增缓存、业务判定或渲染阶段。理论收益仅作方向判断，
不能代替实机测量；若 Embeddium 已消除位置分配，或 consumer 经过未优化包装器，完整入口
仍保持正确，但收益可能明显低于纯 Vanilla BufferBuilder 环境。

5. 青绿色镜片、真实镜体深度遮挡、准星、圆滑法线、CULL 与透明裁切必须与 `sbm.6` 一致。

## `sbm.6-perfdiag.4` 仿射位置变换快路（2026-08-19）

### `perfdiag.3` 实机结论

  `17,751` 个顶点，没有通过漏绘换取性能；

PoseStack 模型矩阵属于仿射变换，位置不需要计算最终不会被消费的齐次 `w`。因此将每次

进一步减少约 `1%–3%` 的顶点阶段耗时，属于低风险增量。法线等尺度快路会改变
浮点归一化路径；把 `scope_body` 接入 TaCZ 原生 `-942` AR layer 则会改变附件的提交时序。
两者都必须单独确认和验证，不与本轮机械修改合并。

## `sbm.6-perfdiag.5` 第一人称 `scope_body` 原生 AR 试验（2026-08-19）

### 优化范围与时序

`perfdiag.3` 已把 HAMR `scope_body` 的同步顶点阶段压到约 `0.254 ms/f`，但它仍占全部
特殊顶点耗时约 90%，并且每帧还要同步提交 `17,751` 个顶点。本轮按用户确认的激进路线，
只把第一人称 scope/scope+sight 的 `scope_body` poly_mesh 接入 TaCZ 1.1.8-hotfix
已经存在的原生 AR stencil layer：

- `-943` 仍负责 `ocular_ring`；
- `-942` 的 before 先同步生成 ocular stencil，随后绘制缓存化的 `scope_body`；
- `-942` 的 after 继续同步绘制 ocular/division 并清理 stencil；
- `-941` 的普通附件模型保持 TaCZ 原有层级。

入口只在第一人称、非 GUI、附件是 scope、`scope_body` 确有 poly_mesh、TaCZ 与本模组 AR
均可用、且 `ocular_ring` 子树没有 poly_mesh 时开启。第三人称、GUI、纯 sight、未安装或
关闭 AR、带 poly `ocular_ring` 的模型全部保留原同步路径。ocular 与 division 仍在 TaCZ
before/after 回调中同步直写；闲置 sight 仍由原生 sight/both 前的既有 Mixin 单独同步补画，
这些节点均不跨 stencil 阶段合批。

`PolyMesh.tryCompileConsumerAccelerated` 只尝试 AR，失败时绝不在 `-942` before 尚未执行的
收集位置直接写顶点；普通 `compileConsumer` 仍保留原来的自动同步回退。若实际 consumer
拒绝或 AR 抛出异常，本故障帧不冒险补画 poly `scope_body`，同时打开实例熔断；后续帧完整
恢复已经验证过的“禁用附件 AR + 同步 TRIANGLES + typed endBatch”路径。熔断只在模型资源
重新加载时复位，避免不稳定 consumer 每帧来回切换。

### 闲置镜片深度兼容

非 AR 路径原有的闲置 `scope_body` `GL_ALWAYS` 深度修复保持不变。AR 路径则精确包装
`renderScopeAccelerated` / `renderBothAccelerated` 中 ordinal 1 的 `-942` before/after：

1. 先执行 TaCZ 原 before，完整生成 ocular stencil 并恢复 AR；
2. 仅在第一人称完全闲置且真实 poly 镜体/镜片条件成立时，把 `scope_body` 改为
   `GL_ALWAYS`，让镜体依靠真实深度遮住青绿色镜片；
3. after 开始前恢复 TaCZ 预期的 `GL_EQUAL, 0`，再执行原 ocular/division 与清理。

开始瞄准后不修改 stencilFunc，因此 ADS、动态圆孔与分划仍完全使用 TaCZ 原层级。回调使用
配置 `-942` 时的状态快照，不在延迟执行时重新读取瞄准进度，避免多视图/后续渲染串状态。

### 新诊断与验收

每五秒新增：

```text
[MeshyPerfDiag] NATIVE_SCOPE_AR attempt=... accepted=... rejected=... circuitTrips=... circuitBypass=...
```

候选状态通常与 `scope_body` 根调用一一对应；在根回调正常完成时满足
`attempt = accepted + rejected + circuitBypass`。`circuitTrips` 只记录模型从关闭切到开启
熔断的首次事件。正常 HAMR 稳态应为 `attempt≈accepted≈1/f`，其余为 0；
`SPECIAL_DETAIL` 的同步直写顶点应由 `19,593/f` 降到约 `1,842/f`，原
`scope_body` 的 `17,751/f` 应等量转入 AR hit/write。稳定期 AR build 应为 0，只在首次使用、
F3+T 或光影状态切换后重建。

需要注意：AR cache lookup/build/mesh.write 的 CPU 入队仍发生在附件调用中，但真正的
`-942` before/after、图层刷新、驱动提交和 GPU 执行可能晚于附件根返回；旧同步路径的
typed flush 则位于附件根内。因此不能把 `perfdiag.4` 与 `.5` 的 `attachmentRoot` 下降直接
当作端到端净收益，必须同时比较 FPS、AR write、同步顶点守恒和画面。

测试矩阵：Battery 无 HAMR、Battery 加 HAMR；光影关闭/开启；第一人称闲置、瞄准过渡、
ADS；纯 scope 与组合镜；第三人称、GUI、掉落物；AR 关闭/移除；F3+T、光影切换和资源重载。
青绿色镜片、镜体真实遮挡、准星、圆滑法线、CULL、division 与第三人称目镜均不得回归。
还应覆盖同帧存在多个不同闲置/瞄准状态 scope 的场景；TaCZ AR 按整数 layer 聚合回调，若未来
让不同 scope 混入同一 `-942`，需重新评估回调集合的顺序，不能依赖实例字段解决。

## `sbm.7` 正式版收口（2026-08-19）

`sbm.7` 将已经完成诊断验证的第一人称 `scope_body` 原生 AR 路径纳入正式版，并新增
`config/taczmeshloader-client.toml` 的 `smoothNormals` 客户端开关。默认值为 `true`，
保持现有枪包的导出逐角点法线；设为 `false` 时只替换 poly_mesh 的法线为逐三角面法线，
不修改顶点顺序、UV、CULL、stencil 或渲染层级。配置在模型构造时快照，修改后需重启或
按 F3+T 重新加载资源。

正式版仍保留 AR consumer 拒绝/异常后的实例熔断与同步 TRIANGLES 回退。性能诊断代码
继续存在，但只有版本号含 `perfdiag` 或显式 JVM 参数启用时才计时、输出日志；普通
`0.1.7-sbm.7` 不进行逐帧计时。

## `sbm.8` 分面法线性能模式（2026-08-19）

`smoothNormals=false` 现在是一条独立的性能路径，而不再只是烘焙结束后覆盖法线：

1. `PolyMesh` 不访问 `normals` 数组，也不读取每个索引元组的 `normalIndex`；UV 仍严格读取
   第三个槽位，顶点位置、UV、三角拓扑、CULL 与 stencil 语义均不变。
2. 每个三角形只把统一面法线乘一次 normal matrix、归一化一次，再复用于三个角点；同步
   TRIANGLES 路径的法线矩阵与平方根运算由每面三次降为一次。
3. QUADS 兼容输出仍保持 `a/b/c/c`，但重复的第四个 C 直接复用第三点的变换结果，不再
   重复位置与法线计算。
4. `smoothNormals=true` 完全保留原逐角点导出法线管线。配置仍在模型构造时快照，修改后
   必须完整重启；不为本开关实现 F3+T、热键或运行时缓存切换。

枪包 JSON 在进入 `PolyMesh` 前仍由 Gson 构建完整 DOM；这里“不读取”指 flat 模式不再
访问、复制、归一化导出法线数据。改为流式 JSON 只能改善加载期内存/耗时，对稳定帧率没有
收益，因此本轮不扩散修改五类模型加载器。旧 VBO 仍保持禁用，因为分面法线也需要随骨骼
旋转和非等比缩放应用 normal matrix，不能用漏掉法线变换的缓存路径换取帧率。
